NTFS TIMESTOMPING DETECTION - UPDATED METHODOLOGY
================================================

CRITICAL CHANGE: FILE-LEVEL DETECTION WITH OH ET AL.'S BEHAVIORAL FEATURES

## Previous Approach Issues (Why We Changed)

OLD APPROACH (Event-Level):
- Merged LogFile + UsnJrnl at event level by timestamp matching
- ~30 hand-crafted features (event_count_in_1min, etc.)
- Trained on individual events
- Result: 46% FALSE POSITIVE RATE (unusable!)
- Problem: Single events too noisy, no behavioral context

ROOT CAUSE:
- Individual events don't have enough context to judge malicious intent
- Legitimate apps create events that look suspicious in isolation
- Example: Temp file created with preset timestamp → counter=3, but benign!

## New Approach (File-Level with Behavioral Analysis)

CORE INSIGHT:
Timestomping is a FILE-LEVEL ATTACK. We need to analyze BEHAVIORAL PATTERNS
across all events for a file, not judge individual events in isolation.

DETECTION LEVEL:
- Train: FILE-LEVEL (predict if file is timestomped)
- Report: EVENT-LEVEL (show all suspicious events for flagged file)

FEATURE SOURCE:
- Oh et al.'s published 3-step methodology (proven approach)
- Not ad-hoc features, but systematic behavioral analysis

## PHASE 1: DATA PREPARATION & CLEANING

### GOAL: Reduce dataset size by 62-82% WITHOUT compromising detection

---

### 1.1: USNJRNL ENRICHMENT

INPUT:
- UsnJrnl CSV from Oh et al.'s tool (352K events per dataset)
- MFT CSV from Phase 0

PROCESS:
1. Parse FileReferenceNumber (hex) to MFT_RecordNumber (decimal)
2. Join UsnJrnl with $MFT on MFT_RecordNumber
3. Add MACE timestamps: SI_CreationTime, SI_ModifiedTime, SI_AccessedTime
4. Normalize all timestamps to UTC+8
5. Handle CSV timestamp mangling (: to . separator, variable milliseconds)

OUTPUT:
- data/processed/phase1/{dataset}_UsnJrnl_enriched.csv
- Size: 352K events (no reduction yet, just enrichment)

---

### 1.2: USNJRNL AGGRESSIVE FILTERING

INPUT: Enriched UsnJrnl from 1.1

PROCESS - 3-Stage Filtering:

STAGE 1: Keep ALL Basic_Info_Changed Events (~34K)
- These are potential timestomping events (BDP detection core)
- Rationale: Any Basic_Info_Changed could be timestomping

STAGE 2: Keep FIRST File_Created Event Per File (~55K)
- One creation event per FileReferenceNumber
- Rationale: Only need ONE creation time per file for comparison
- Drops duplicate creation events (same file created multiple times in journal)

STAGE 3: Keep Delete/Rename at Monitored Paths Only (~50K)
- Only keep delete/rename events at paths where we have creation events
- Rationale: Tunneling can only affect files we're monitoring
- Filters out 56% of delete/rename events at irrelevant paths

WHAT GETS DROPPED (218K events, 62%):
- Pure data operations: Data_Added, Data_Overwritten (alone)
- Metadata changes: Access_Right_Changed, Extended_Attr_Changed (alone)
- Duplicate creation events: 2nd, 3rd, ... creation for same file
- Delete/Rename at unmonitored paths: Events we can't use for detection
- File_Closed events alone: Not useful without Basic_Info_Changed

OUTPUT:
- data/processed/phase1/{dataset}_UsnJrnl_filtered.csv
- Size: 134K events (62% reduction)
- Detection capability: 100% preserved (all ground truth events included)

### 1.3: LOGFILE FILTERING

INPUT: LogFile CSV from Oh et al.'s tool (already parsed!)

PROCESS:

NOTE: LogFile already has MACE timestamps (no $MFT join needed!)

OUTPUT:

## PHASE 2: FEATURE ENGINEERING (FILE-LEVEL)

### GOAL: Calculate Oh et al.'s behavioral features at file level

---

### 2.1: USNJRNL FILE-LEVEL FEATURES

INPUT: Filtered UsnJrnl from Phase 1

PROCESS:
1. Parse timestamps (handle CSV mangling)
2. Group events by FileReferenceNumber
3. For each file, calculate:

FEATURES (Oh et al.'s methodology):
- file_event_count: Number of events for this file
- file_has_creation: 1 if File_Created event exists
- file_creation_time: Timestamp of first File_Created event
- file_has_bdp: 1 if BDP (Basic_Info_Changed + File_Closed within 1s) exists
- file_last_bdp_timestamp: Timestamp of last BDP event
- file_has_tunneling: 1 if tunneling detected (Step 3 below)
- file_behavior_counter: 0-5 score (Step 4 below)
- zero_nanoseconds: 1 if any timestamp ends in .000 (manual setting indicator)

STEP 3: TUNNELING DETECTION (Vectorized, <30 seconds)
- Merge creation events with delete/rename events on FullPath
- Filter to different FileReferenceNumbers (DIFFERENT files reusing same name)
- Check if delete/rename happened 0-15 seconds BEFORE creation
- CRITICAL SANITY CHECK: SI-C diff must be < 1 day
  (Real tunneling won't cause huge discrepancies like 5 days)
- If SI-C diff > 1 day → NOT tunneling, likely timestomping

STEP 4: BEHAVIOR COUNTER CALCULATION (Per File)
counter = 0

# Case 1: Creation event vs SI-C comparison
if file_has_creation AND |SI_CreationTime - file_creation_time| > 5 seconds:
    counter += 1

# Case 2: Last BDP vs SI-C comparison
if file_has_bdp AND |SI_CreationTime - file_last_bdp_timestamp| > 5 seconds:
    counter += 1

# Case 3: Tunneling adjustment
if counter >= 1:
    if file_has_tunneling:
        counter -= 1  # Legitimate Windows behavior
    else:
        counter += 2  # Suspicious (no legitimate explanation)

# Final: counter ranges 0-5
# 0 = clean, 1 = slightly suspicious, 2-3 = suspicious, 4-5 = highly suspicious

LABELING (Training Datasets Only):
- Load suspicious.csv for this dataset
- Extract USNs for timestomped events
- Label file as timestomped if ANY of its events in suspicious list:
  file['is_timestomped'] = 1 if any(usn in suspicious_usns for usn in file['USN_list']) else 0

VALIDATION DATASETS:
- NO LABELING! Keep is_timestomped = None
- Labels only used in Phase 4 for evaluation

OUTPUT:
- data/processed/phase2/{dataset}_UsnJrnl_file_features.csv
- Size: ~65K files (down from 134K events, 82% total reduction from original!)

---

### 2.2: LOGFILE FILE-LEVEL FEATURES

INPUT: Filtered LogFile from Phase 1

PROCESS:
1. Parse Detail column (before → after timestamps)
2. Group events by FullPath
3. For each file, calculate:

FEATURES (Oh et al.'s LogFile methodology):
- file_event_count: Number of timestamp change events
- si_c_change_count: Count of SI-C changes
- si_m_change_count: Count of SI-M changes  
- si_c_reversal_direction: "past", "future", or "both"
- si_m_to_past: 1 if SI-M changed to past (suspicious)
- file_has_tunneling: 1 if tunneling detected (bidirectional 15s window)
- zero_nanoseconds: 1 if changed timestamp has .000
- file_behavior_counter: Similar logic to UsnJrnl counter

CONTEXT-AWARE DETECTION:
Case 1: File created immediately before timestamp change
  → Only check SI-C changes (SI-M changes normal after creation)
  
Case 2: No recent creation (existing file)
  → Check SI-C changes OR SI-M changes to past

TUNNELING DETECTION (LogFile-Specific):
- CRITICAL: LogFile records often OUT OF ORDER
- Timestamp change record created FIRST, then delete/rename records
- Check ±15 seconds (bidirectional), not just backwards
- Or check by LSN proximity instead of time

LABELING (Training Only):
- Load suspicious.csv, extract LSNs
- Label file if any of its events in suspicious list

OUTPUT:
- data/processed/phase2/{dataset}_LogFile_file_features.csv

---

### 2.3: MERGE FILE FEATURES (LogFile + UsnJrnl)

INPUT:
- UsnJrnl file features from 2.1
- LogFile file features from 2.2

PROCESS:
1. Merge on file_path (OUTER JOIN - keep files from either source)
2. Calculate combined features:
   - max_behavior_counter = max(usnjrnl_counter, logfile_counter)
   - has_both_sources = 1 if file has events in both sources
   - combined_suspicion_score = weighted average of counters
3. Combine labels (file timestomped if flagged in EITHER source)
4. Handle NaN features (fill with 0 or keep as NaN for tree models)

FINAL FEATURE SET (~20-25 features):
# Source indicators
- has_usnjrnl_events (0/1)
- has_logfile_events (0/1)
- has_both_sources (0/1)

# UsnJrnl features (NaN if no usnjrnl events)
- usnjrnl_event_count
- usnjrnl_behavior_counter
- usnjrnl_has_bdp
- usnjrnl_has_tunneling
- usnjrnl_has_creation
- usnjrnl_si_c_diff_max

# LogFile features (NaN if no logfile events)
- logfile_event_count
- logfile_behavior_counter
- logfile_si_c_change_count
- logfile_si_m_to_past
- logfile_has_tunneling
- logfile_zero_nanoseconds

# Combined features
- max_behavior_counter
- combined_suspicion_score
- zero_nanoseconds (from either source)

# Label (training only)
- is_timestomped (0/1)

OUTPUT:
TRAINING:
  - data/processed/phase2/combined_training_features.csv
  - All 22 training datasets combined into ONE file
  - ~1.4M files total
  - Has 'is_timestomped' label (~264 positives)

VALIDATION:
  - data/processed/phase2/{dataset}_validation_features.csv
  - Each validation dataset saved separately (5 files)
  - NO 'is_timestomped' label (blind test)

## PHASE 3: MODEL TRAINING (FILE-LEVEL)

INPUT: Combined training features (1.4M files, 264 positives)

PROCESS:
1. Load combined training data
2. Train/test split: 80% train, 20% test (from training data only)
3. Handle class imbalance (1:5,300 ratio):
   - SMOTE oversampling on training set only
   - Class weights for cost-sensitive learning
   - Threshold optimization for F1 or precision/recall balance
4. Train 4 models:
   - Random Forest (ensemble baseline)
   - XGBoost (gradient boosting)
   - LightGBM (fast gradient boosting, handles NaN natively)
   - Logistic Regression (linear baseline)
5. 5-fold cross-validation for each model
6. Feature importance analysis
7. Save best model (highest F1 on test set)

EVALUATION METRICS:
- Confusion matrix
- Precision, Recall, F1-score
- ROC-AUC, Precision-Recall curve
- False Positive Rate (CRITICAL - must be <5%)

OUTPUT:
- models/random_forest.pkl
- models/xgboost.pkl
- models/lightgbm.pkl
- models/logistic_regression.pkl
- results/phase3/model_comparison.csv
- results/phase3/feature_importance.csv
- results/phase3/confusion_matrices.png

VALIDATION DATASETS NOT USED HERE!
They remain completely unseen for blind testing in Phase 4.

## PHASE 4: VALIDATION & REPORTING

INPUT:
- Trained models from Phase 3
- Validation features (from Phase 2, unlabeled)
- Ground truth (suspicious.csv, only for evaluation)

PROCESS (For Each Validation Dataset):
1. Load validation features (NO labels)
2. Run predictions with all 4 models
3. Load ground truth from suspicious.csv
4. Convert ground truth to file-level (event USN/LSN → file is_timestomped)
5. Compare predictions vs ground truth
6. Calculate metrics: Precision, Recall, F1, FPR
7. Analyze:
   - Which files were correctly detected?
   - Which files were missed? (false negatives)
   - Which benign files were flagged? (false positives)
8. Generate detailed reports

OUTPUT (Per Validation Dataset):
- results/validation/{dataset}/summary_report.txt
- results/validation/{dataset}/flagged_files.csv
  (Files predicted as timestomped with confidence scores)
- results/validation/{dataset}/predictions.csv
  (All files with 0/1 predictions)
- results/validation/{dataset}/predictions_with_features.csv
  (Full feature set for analysis)
- results/validation/{dataset}/confusion_matrix.png
- results/validation/{dataset}/event_details.csv
  (For flagged files, show all UsnJrnl and LogFile events)

AGGREGATE OUTPUT:
- results/validation/overall_performance.csv
  (Metrics across all 5 validation datasets)
- results/validation/best_model_selection.txt
  (Which model performed best on validation)
- results/validation/error_analysis.txt
  (Common patterns in FP and FN)

SUCCESS CRITERIA:
- Recall: 85-90% (detect most timestomped files)

- F1-score: 85-90%

## CRITICAL SUCCESS FACTORS

1. TUNNELING DETECTION ACCURACY
   - Must correctly identify legitimate vs malicious timestamp changes
   - SI-C diff sanity check (<1 day) is critical
   - If wrong, behavior counter decreases and we miss detection

2. BEHAVIOR COUNTER CALIBRATION
   - Threshold (2, 3, or 4?) affects precision/recall tradeoff
   - Optimize on validation set

3. CLASS IMBALANCE HANDLING
   - SMOTE + class weights critical
   - Only 264 positives across 1.4M files

4. VALIDATION DATASET BIAS
